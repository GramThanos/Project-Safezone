# AGENTS.md

Orientation for anyone working in this repository, covering what you need to find your way around.

## What it is

**Project Safezone** is a web manager for Project Zomboid dedicated servers. Players sign up, link their in-game characters to their account, and earn loot that is delivered into the running game. Staff monitor and control servers, run whitelisted console actions, and review an audit trail.

The stack is **6 containers** (`docker-compose.yml`):

| Service       | Tech                                 | Published         |
|---------------|--------------------------------------|-------------------|
| `game-server` | Python + SteamCMD + supervisord      | `16261-16262/udp` |
| `backend`     | Flask + Gunicorn                     | internal only     |
| `scheduler`   | backend image, `python -m scheduler` | internal only     |
| `frontend`    | React + Nginx                        | `8080` -> `80`    |
| `db`          | MariaDB 11                           | internal only     |
| `cache`       | Redis 7                              | internal only     |

Only the frontend and the game's UDP ports are reachable from the host. The backend API and the manager API sit on the `internal` network - reach them through the frontend's Nginx (`/api` and `/health` are proxied) or by exec-ing into a container.

**The split that matters:** the *backend* owns accounts, characters, claims, loot and site content. The *game-server manager* owns servers, tasks and the console boundary. The backend has no `Server` or `Task` model; it proxies to the manager's HTTP API with a shared `API_TOKEN`. Never invert that dependency - the manager does not call the backend.

## Backend (`backend/`) - Flask REST API

- `app.py` - blueprint registration, CORS, security headers, and `/` and `/health`. Version from `Config.APP_VERSION` (`2.0.0`). There is no rate limiting: it was removed deliberately, so load on a hot read is answered with caching rather than a limiter.
- `init_db.py` - runs Alembic migrations, seeds box types and the default admin. Idempotent; `entrypoint.sh` runs it on every boot. Exit code `75` means "the database is not up yet" and is the only one the entrypoint retries.
- `alembic/versions/` - **the schema lives here.** A new model means a new migration; there is no `create_all` bootstrap on this side.
- `scheduler.py` - separate worker process for recurring jobs. It claims work with `SELECT ... FOR UPDATE`, so running more than one is safe. It also pumps the alert event queue on every tick - deliberately not a job, since job intervals are floored at a minute and new job kinds register switched off, neither of which suits an event pump.
- `src/config.py` (`configure_app()`), `src/database.py`.
- `src/middleware/auth.py` - JWT plus `token_required` / `moderator_required` / `admin_required`. Role, ban state and `token_version` are re-read from the database on every request, so a ban, a demotion or `logout-all` takes effect immediately. Sessions slide: a token carries a session id (`sid`), and `POST /api/auth/refresh` is the session check - `AuthContext` calls it on opening, on returning to the tab and every five minutes while visible, in place of `/me`. It answers 401 for a session that has ended (and the client signs out), returns the current account, and hands back a new token with the same `sid` only once the current one is due (`token_needs_renewal`: an hour old, or half its lifetime, or the client kind changed), so frequent checks do not churn tokens. The installed app declares itself with `X-Client: app` and gets `app_session_days` instead of `token_expiry_hours` - client-declared, so a choice of length rather than a security boundary. An account with `must_change_password` can reach almost nothing until it does.
- `src/models/` - `user`, `auth_token`, `ban`, `character`, `claim_request`, `reward`, `box`, `event`, `event_box`, `box_loot_pool`, `user_box`, `inventory_item`, `invitation`, `notification`, `staff_alert`, `report`, `audit_log`, `app_setting`, `scheduled_job`, `alert_channel`, `push_subscription`, `shop_category`, `shop_item`, `shop_item_category`, `shop_purchase`, `coin_log`.
- `src/routes/` - blueprints: `auth`, `characters`, `claims`, `servers`, `site`, `boxes`, `inventory`, `invitations`, `notifications`, `reports`, `push`, `shop` (`/api/coins` and `/api/shop`), `shop_admin` (`/api/admin/shop`), `leaderboard` (`/api/leaderboard` and the staff view `/api/admin/leaderboard`), `rewards` (mounted at `/api/admin/rewards`) and `admin` (`/api/admin` - the large one: users and their coin balances, servers, installation, mods, claims, boxes and their pools, events, actions, give, tasks, audit, settings, jobs, reports, alert channels, the staff feed).
- `src/utils/` - `settings` (runtime-editable config), `jobs` (scheduler job registry), `game_server` (proxy helper), `character_info` (a linked character's saved game data: fetched, cached and cut to its reader), `redis_utils` (live state and online roster), `actions` (console-action catalog access), `loot`, `events` (reads the box/event config during a grant), `daily`, `expiry`, `notify` (in-app messages to *one player*), `coins` (the balance, the gain log, prices, earning sources and the life rule), `leaderboard` (the cached board, its exclusions and the public allowlist), `moderation`, `audit`, `alerting` (the staff event catalog, routing, cooldown and the game-event queue), `channels` (how each kind of destination is written), `mailer` (composes mail; the game-server sends it), `push` (who gets a browser notification; the game-server sends it), `captcha`, `paging`, `logging_setup`.

**Roles:** `banned` < `player` < `moderator` < `admin`.

**Characters are claimed, never created.** `POST /api/claims` **auto-approves** when the given in-game name is currently online on the server - being online is the proof of ownership. Staff can revoke afterwards (`POST /api/admin/claims/<id>/revoke`). The other way round, staff see the characters in each server's save that nobody is linked to (`GET /api/admin/claims/unlinked`, read through the manager's `GET /api/servers/:id/characters`), and an admin may link one to an account by hand (`POST /api/admin/claims/link`) - the save stands in for the online check as proof the character exists, and the admin's word for ownership, so it is audited as `claim.staff_link`. And `DELETE /api/characters/<id>` is an *unlink*: it releases the in-game identity for anyone to claim again.

**Loot flow:** boxes are named records with their own loot pool; **events** decide which box a player receives by a weighted pick from a line-up. `POST /api/boxes/daily` grants everything currently due - the daily event's box plus one from each active custom event (custom events stack on top of the daily box; a custom event's cadence is `daily` or `once`), each guarded by a unique `(user_id, event_id, period_key)` so a repeat claim grants nothing new; the day boundary follows the primary server's timezone. The weekly bonus is granted by the same claim that collects the week's threshold-th daily box (`events.grant_weekly_bonus`), keyed to the week's Sunday; the `weekly_streak_bonus` job is only a catch-up for a week whose last claim could not pay it. Open a box to draw rewards into inventory -> `POST /api/inventory/send` to an online linked character, which queues a `give_reward` task on the manager. **An inventory row is a bundle**: a reward with the amount it was won in (`count`, captured from the pool entry or the listing), and getting a reward twice is two rows - the page stacks rows of the same reward *and* amount and shows both numbers apart ("3 bundles of 5"). Bundles are sent, sold and discarded whole, never split. A send is several bundles of one stack as **one** task (`bundles: [{ref, count}]`, at most 20, or 5 for usables since each runs the whole sequence): the manager packs whole bundles into `additem` lines under its 100-per-line cap, or runs a usable once per bundle, and reports the ones that landed in `delivered_refs`, so a delivery that stops part-way hands back only what is still owed. The backend reconciles per task, so a stack is one notification however many bundles it carried. A reward is either an **item** (`additem`) or a **usable**: an admin-authored free-text `commands` sequence (one or more console lines, optional `sleep`/`wait` pauses handled by the executor, `{{USERNAME}}` substituted for the recipient). The command text is trusted because only an admin can author a reward; the game-server stays the command boundary, validating the sequence when it is saved (`POST /api/rewards/preview`) and re-validating the recipient name before it reaches the console. Note this deliberately lifts the old catalog-only restriction, so a usable reward *can* now run any console command an admin types - the safety comes from admin authorship, not a whitelist. (Staff Give and account-ban actions still use the typed `droppable`/`min_role` catalog.) Delivery is *acknowledged*, not assumed: the task waits for `cmd_ack:<id>` in Redis, and un-acked items go back to the player. An admin can take loot away from an account's manage page (`/admin/users/<id>`): an unopened box is marked `revoked` rather than deleted, because its row is also the `(user_id, event_id, period_key)` guard and deleting it would let the player claim it again; a held or failed inventory item is deleted outright, and one mid-delivery cannot be touched.

**Coins are a balance plus a log of gains** (`src/utils/coins.py`, off until `coins_enabled`). `users.coin_balance` changes only through relative `UPDATE`s in the caller's transaction - `debit` adds `WHERE coin_balance >= n`, so spending is refused in the statement that would overdraw. Every gain goes through `coins.earn`, which also writes `coin_log` (source, amount, quantity, character): a sale, playing, a staff grant, and any source added later. Spending is not in that log - purchases are `shop_purchases` rows and staff deductions are audited. Both logs are history, not state: `prune_coin_log` trims them to `coin_log_retention_days` (90 by default, never under 2, since the daily summary reads yesterday and a daily limit reads today), so every total shown is a counter on its own row - `users.coin_balance`, `characters.coin_earned`, `shop_items.sold` - and never a sum over the log. **Selling back** is the inventory discard: with coins on, `POST /api/inventory/remove` pays each held or failed bundle its reward's `coin_value` - once per bundle, whatever it holds - in the transaction that deletes it; the page sells one bundle at a time. `inventory_items.sellable` is only False on rows from when a send could split a holding (the value stayed with the part left behind) and is still honoured for them. **Earning by playing** is `coins.SOURCES`, a registry of counters read from the save (zombie kills today); each character keeps `coin_progress` per source - `counted` (paid for) and `seen` (last reading) - set to its current counts when it is linked, so nothing from before the link pays, and moved by whole steps so the rest carries. Lives are told apart by the character's name in the save (`coin_identity`, with earlier names in `coin_identities`): a new name is a new character counted from zero; a name seen before, or any counter that drops without a new name, is a restored backup or a rollback and re-baselines without paying - so restoring a world never pays its kills twice. A reading whose save is no newer than `coin_saved_at` only stamps `coin_checked_at`. Settlement rides along whenever a character's data is fetched anyway (the owner's and staff views, `GET /api/coins/characters` behind the Characters page's coin box, and an unlink, which settles first), plus the daily `settle_coins` job: one `POST /api/servers/:id/characters/snapshot` per server, which makes a running server with players online `save` and waits for `players.db` to change and go quiet before returning every account's main character. Payments do not notify one by one; `coin_report` (hourly, once per day behind a Redis mark that fails closed) sends each player one "yesterday you earned" message from the log. **The shop** (`shop_categories`, `shop_items`, `shop_item_categories` - a listing may be in several categories) sells catalog rewards into the inventory with their own expiry (`shop_item_expiry_days`) and an optional per-listing `daily_limit`, counted in `shop_purchases` against the primary server's day with the buyer's user row locked so two purchases cannot both slip under it. A listing's price is stored - the panel suggests 20x the sell value - but never below the sell value (`coins.min_price`), checked when a listing is saved and when a reward's value is raised. A purchase carries the price the player saw and is refused if it changed.

**The leaderboard names characters, never accounts.** The manager's `GET /api/servers/:id/leaderboard` returns every *living* owned row of `players.db` (split-screen slots included, the dead and single-player rows left out), with the owner's username so the backend can apply exclusions; `src/utils/leaderboard.py` caches that raw save per server (a minute fresh, a day as a stale fallback) and decides who is hidden on every read, so a new exclusion or ban applies at once. Hidden is `leaderboard_excluded` (in-game owner or linked account username, without case) or, with `leaderboard_hide_banned` on, a character linked to a banned account. What a browser gets is the allowlist `PUBLIC_FIELDS`. `leaderboard_visibility` is `public`, `authenticated` or `disabled` (an unknown value reads as disabled); `GET /api/admin/leaderboard` is moderator-readable whatever it says and shows the owner, the linked account and why a row is hidden. The three settings are group `leaderboard`, edited on the admin Leaderboard screen, not Settings.

**Settings are two-layered.** Every key in `src/utils/settings.py::REGISTRY` has a default - an environment variable, or a literal for the handful with no variable behind them - and an optional `app_settings` row as a live override, editable in the admin panel by an admin only. Only registered keys are readable or writable. Registration control (open / closed / shared password / invitations) works this way - independent switches, not a mode.

Anything an operator might reach for *during* an incident is in there: registration, loot and retention policy, session length and the SMTP settings. Mail is the odd one - its environment default lives in the *game-server* container, so a blank host in the panel means "use that", and a filled-in one is sent with each message to the relay. A spec may carry `validate` for anything dangerous to mistype.

## Game Server Manager (`game-server/`)

Based on `cm2network/steamcmd`. Four processes under `supervisord`, all in `src/` (copied to `/app`):

1. `manager_api.py` - Flask API on port `5000`, internal only. Bearer `MANAGER_API_TOKEN` (auth is skipped when no token is configured). This is what `GAME_SERVER_API_URL` points at.
2. `manager_tasks.py` - task worker (`pending` -> `processing` -> `completed`). Reacts to pub/sub and also sweeps every `TASK_SWEEP_INTERVAL`, so a lost notification delays a task rather than stranding it.
3. `manager_game.py` - runs and monitors the game process, and publishes live state and the online roster to Redis (`server:<id>:state`, `server:<id>:online_players`), which the backend reads for the UI, claims and reward delivery.
4. `manager_maintenance.py` - checks for game and mod updates and carries maintenance runs out (see below). Its own process because a run spends most of its life waiting, and the task worker is a single queue that reward deliveries sit behind.

Modules: `config`, `database`, `models` (`Task`, `Server`, `ServerPlayerCount`, `WorkshopCollection`, `MaintenancePolicy`, `MaintenanceRun`), `cache`, `servers`, `tasks`, `commands` (**the command-injection boundary**), `actions` (whitelisted PZ admin commands with typed parameters and `droppable` / `min_role` flags, exposed as `GET /api/actions` so the backend never re-implements the rules), `rcon`, `roster` (pure parser for `players` output), `items` (the in-game item catalog behind the reward picker - PZwiki's autogenerated item list parsed from raw wikitext, cached in Redis under one never-expiring key and refreshed on age so a wiki outage degrades to a stale list rather than an empty one; base-game items only), `server_config` (PZ INI), `mods` (on-disk library, `mod.info` parsing, `require=` checking; deliberately offline and dependency-free so it stays testable), `workshop` (Workshop item titles/descriptions from Steam's keyless `GetPublishedFileDetails`, Redis-cached, stdlib `urllib` so it adds no dependency, and degrades to no-metadata rather than failing), `backups`, `logs`, `steam`, `webhook` (the Discord relay - a hole in the egress boundary, so its allowlist is tested), `mailer` (the SMTP relay, for the same reason: the backend cannot reach a mail server either), `push` (the browser push relay - payloadless Web Push signed with a VAPID key it creates on the game_data volume, sent only to the browser vendors' push services because the endpoint comes from a player's browser; that allowlist is tested), `events` (the queue of player/server events the backend's scheduler drains), `maintenance` (the pure rules: cron, the policy and its validation, what is out of date, when a planned run goes, which countdown warning is due), `maintenance_store` (the policy, runs, hold and check results in the database and Redis, shared by the API and the worker), `characters` (one account's character out of a server's `players.db`, via the vendored `zomboid_db_api` package, or every account's main character in one pass for the coin snapshot; the parsed file is kept until it, its WAL or `WorldDictionary.bin` changes).

Task actions: `update_server` (optional per-task `beta` to switch branch; refused while any server is outside `stopped`/`failed`/`maintenance`, except for a first install), `uninstall_server` (deletes what SteamCMD installed, keeping configs, worlds and - unless `keep_mods` is false - the Workshop library; refused unless every server is `stopped` or `failed`, since a sleeping or relaunching one can put a live process on a half-deleted install), `get_app_info`, `give_reward`, `run_action` (same handler, staff-initiated), `backup_world`, `restore_world`, `update_mods` (reconciles what a server's INI already lists), `download_workshop` (installs explicit ids, which is how a *new* mod arrives). `reap_stuck()` fails tasks abandoned in `processing` by a restart.

Steam: PZ dedicated server `STEAM_APP_ID = 380870`, branch via `STEAM_APP_BETA`, installed to `STEAM_INSTALL_DIR` (`/opt/steam-apps`). Heap and GC are sized at launch from the container's limits (`GAME_SERVER_MAX_HEAP=auto`, `GAME_SERVER_GC=auto`).

**A sleeping server is emulated, not absent.** `manager_game.py` answers Steam A2S queries and RakNet pings on the game ports while the process is down, so the server stays listed and joinable-looking. Two things make that work. The A2S family is behind an IP-bound HMAC challenge (anti-spoofing, anti-amplification); the RakNet ping deliberately is not, because its unconnected ping has no challenge step and its amplification factor is low. And the reply has to carry a *version the client recognises* or it shows as ping -1 and no join is offered - build 42 compiles its version in rather than writing it to disk, so it is scraped from the server's own boot log (`_maybe_capture_version`, once per launch) and cached to `GAME_VERSION_CACHE_FILE` to be replayed while asleep.

**Waking is a heuristic, and knowingly so.** A direct-IP join really is a UDP packet (`OPEN_CONNECTION_REQUEST_1`) and wakes the server outright. A *Steam* join never reaches the port at all - it is brokered by Steam's network - so the only signal is the client's A2S query: `WAKE_A2S_THRESHOLD` authenticated `A2S_INFO` queries from one address within `WAKE_A2S_WINDOW` count as somebody trying to join. Accumulating per source is what separates a player sitting on the connect screen from a browser sweep touching thousands of servers once each. False wakes from a server-list refresh are accepted by design; set the threshold to 1 to wake on first contact. `WAKE_DEBUG` traces every datagram for diagnosing a server that will not wake - off by default, because the port is public and the trace records player IPs.

**Installing is admin-only; switching mods on and off is not.** A moderator may edit which of the *downloaded* mods a server loads (`PUT /api/admin/servers/:id/mods`, which sets `downloaded_only` for any non-admin so the manager refuses newly-added ids or names that are not on disk) - that is the 3am repair. Installing game files, downloading Workshop items, deleting them, and `POST /api/admin/tasks` (free-form action, so it could reinstall the game) are all `@admin_required`.

**Collections are remembered for their order.** `workshop_collections` stores each collection installed from, with its items in the author's `sortorder` - frequently the intended load order for Project Zomboid. A table rather than a cache entry because losing it to an eviction silently downgrades "enable all of this, in order" back into dozens of manual clicks. Written by `download_workshop` only after the items are really on disk. `mod.info`'s `require=` is parsed into `requires`, and `mods.check_requirements()` reports a dependency that is missing from a load order or that loads after the mod needing it.

**Three sources of mod naming, deliberately kept apart.** `mod.info` on disk gives the *mod* id, name and description (offline, only after download). `workshop.lookup()` gives the *Workshop item* title and summary for any id, before download, and is what tells a typo from a real item - SteamCMD reports success for an id that does not exist, so this is the only cheap way to catch one. Browsing or searching the Workshop would need `IPublishedFileService/QueryFiles` and a Steam Web API key; not implemented. `workshop.collections()` is the keyless substitute - `GetCollectionDetails` expands a collection id into its items in the author's `sortorder`, and doubles as the way to tell a collection id from an item id, since their URLs are identical.

**Staff alerts are one registry and three kinds of channel.** `src/utils/alerting.py` holds the event catalog, the cooldown and the dispatcher; `alert_channels` rows are the destinations - a Discord webhook, the staff feed, an ops mailbox - each subscribing to the events it wants, and `src/utils/channels.py` decides how each kind is written. A message carries `detail` for the internal channels only, which is how the text of a report reaches the moderators without reaching a Discord channel that has a wider membership.

**The staff feed is one row, not one per moderator.** The in-app destination writes a single `staff_alerts` row that every moderator and admin reads, and `users.staff_alerts_read_at` carries the only genuinely per-person part - how far each of them has got. It used to write a `notifications` row per moderator, which put deployment news in the same inbox and the same unread badge as the messages a *player* gets about their own account, and cost ten rows per join on a ten-moderator deployment. `GET /api/admin/staff-feed` is **moderator**-readable, because it replaces notifications moderators already received; configuring the channels stays admin-only. Being a chronological record of what actually fired, it is also the answer to "is any of this working" - a Discord channel that is quiet because nothing happened and one whose webhook was deleted look identical from the Alerts screen. It is a feed rather than a record, so `prune_staff_alerts` trims it (`staff_alert_retention_days`, a month by default) where the audit log keeps forever.

**A linked character's game data comes from the save.** `zomboid_db_api` (vendored under `game-server/src/`, standard library only) decodes `Saves/Multiplayer/<server>/players.db` read-only, so it is as fresh as the game's last save of that character. The manager's `GET /api/servers/:id/characters/:username` returns the whole decoded report; the backend's `character_info` decides who sees what. Two rules hold it together. The character is found by its **owner** (`getPlayersByOwner`) and never by `getPlayer`, which also matches a character's in-game name - anyone can name a character after somebody else's account. And what reaches a browser is an **allowlist** (`owner_view`, `staff_view`): the Steam ID, admin and cheat flags, the chat tag and mod data never leave the backend, and the zombie infection is staff-only, because in the game a player does not know until the symptoms show - including a wound that exists only because of the infection. `GET /api/characters/:id/game` is the owner's; `GET /api/admin/characters/:id/game` is moderator-readable and audited (`character.view`), so the staff UI loads it only when asked. Redis holds the raw report (`charinfo:<server>:<username>`), fresh for a minute and served as `stale` for a day when the game-server cannot answer; a 404 replaces it.

**Only staff-facing events are routable.** A message to a *player* about their own account goes through `notify.py` to the person concerned, and account mail (verification, reset) is part of how those flows work. Neither is in the registry, because neither is something an operator should be able to switch off.

**The sending is split across the two services on purpose.** The backend decides who hears what; the manager owns the sockets - `POST /api/webhook` for Discord, `POST /api/mail` for SMTP - because `internal: true` leaves the backend with no egress and no DNS. Backend-side events are emitted at their call site on a background thread. Events only the manager can see (a player joining, a server giving up) are pushed onto a Redis list by `events.py` and drained by the scheduler, because the manager still does not call the backend.

**Crate reminders are browser push, and deliberately payloadless.** A player turns them on per device (`usePush`, from the profile or the app's Me tab), which registers `frontend/public/sw.js` - a worker with no fetch handler, so it changes nothing about how the site loads - and stores the subscription in `push_subscriptions`. The `crate_reminder` job runs every five minutes, does nothing until `crate_reminder_time` in the primary server's timezone, then once per day (a Redis mark that fails closed) sends to every device whose player has no daily box for today, with a TTL that ends at midnight. A push with no body needs only a signature, not RFC 8291 encryption, so the reminder's words live in the service worker; anything other than the crate reminder needs a payload first. Web Push has no batch call, so grouping is everything around it: one relay call per 500 devices, one VAPID token per push service, and a few kept-alive connections per service. A device reported gone, or an endpoint the relay refuses, is deleted. A subscription also belongs to the session it was made in (`session_id`, `session_expires_at`, `token_version`): a refresh extends it, and one whose session has expired or was ended is never sent to and is deleted by the job. Signing out releases both sides (`services/push.js`); signing in again on a device that still has a browser subscription re-binds it.

**Maintenance takes every server down, never one.** One install and one Workshop library serve them all, so any update - game or mod - is applied with the whole stack held down. A run (`maintenance_runs`) goes `scheduled` -> `announcing` (the in-game countdown) -> `stopping` -> `updating` -> `completed`/`failed`, or `cancelled` from anything before `updating`; at most one is open, and updates found while it waits are folded into it. The **hold** is a Redis key (`MAINTENANCE_HOLD_KEY`) the worker keeps alive on a short TTL *exactly* while the run is `stopping` or `updating` - derived from the run on every tick, so a cancel or a failure releases it by changing the run, and a dead worker cannot strand the servers. While held, `manager_game` stops the game and the wake listener, refuses to launch, and publishes `maintenance`, but leaves the desired state alone, so each server returns to what it was doing. The update runs inline as a task (`tasks.run_inline`), so it shows on Tasks without queueing behind deliveries. The policy is one JSON row (`maintenance.DEFAULT_POLICY` fills anything missing): automatic checks on cron schedules read in the primary server's timezone, extra checks when a server goes quiet, per-kind approval, apply-when-empty, a maintenance window, a maximum wait, the countdown and its message, and excluded mods. A cancel stops the same updates being planned automatically before the next window. Moderators may read maintenance and cancel a run; everything else is admin-only. The Workshop has no version numbers, so a mod update is detected by comparing the Workshop's `time_updated` with the `timeupdated` Steam recorded in `appworkshop_108600.acf` - one clock on both sides.

**Outbound network access lives here, not in the backend.** `backend` and `scheduler` sit only on the compose `internal` network, which is declared `internal: true` - no egress and no DNS, so anything reaching a third party (`workshop`, `items`, SteamCMD) has to run in this container and be proxied. That is deliberate: giving the backend egress would hand outbound access to the service holding authentication and untrusted user input. If you add an integration that needs the internet, put it here.

**One install serves every server.** There is a single `STEAM_INSTALL_DIR`, and Workshop content lands inside it under `steamapps/workshop/content/108600/`, shared by all servers. So the install and the mod library are *host* state (`GET /api/installation`, `GET /api/mods`, `DELETE /api/mods/:item_id` - no server id), and only the selection is per-server (`GET`/`PUT /api/servers/:id/mods`, writing that server's `WorkshopItems` and `Mods`). `steam.installed_app_state()` reads Steam's own `appmanifest_380870.acf` for the installed build id; `get_app_info` asks Steam for the available one. Comparing the two is the only reliable staleness check.

## Frontend (`frontend/`) - React SPA

React 18 + React Router 6, built with Vite, Nginx in production, dark Bootstrap 5 theme.

- `src/pages/` - `Home`, `SignIn`, `ForgotPassword`, `ResetPassword`, `VerifyEmail`, `Servers`, `Characters`, `Rewards`, `Shop`, `Profile`, `Notifications`, `Reports`, `Leaderboard`, `LegalPage`, `Me` (the app's Me tab).
- `src/pages/admin/` - nested routes under `/admin` (`AdminLayout` + `Outlet`): servers (plus detail, logs, config, form), installations, tasks, users (plus a per-user manage page), claims, rewards, boxes, shop, events, give, invitations, reports, jobs, alerts, staff feed, settings, branding, legal, about, audit. `Installations` owns maintenance (`MaintenancePanel`), the game files and the mod library; `Tasks` is the queue and its output, and starts nothing.
- **App mode** - installed to a phone's home screen, the site swaps its navbar and footer for a title bar (`AppHeader`, with a back button, since an iPhone home-screen app has none) and a bottom tab bar (`TabBar`); the rest of the menu and footer moves to `/me`. `public/assets/app-mode.js` makes the one decision - standalone display mode *and* a touch screen with a phone's viewport - before first paint, and sets `<html data-app="phone">`; `src/index.css` keys off that attribute and React reads it through `useAppMode`. A browser, a desktop install and a tablet all keep the website. It is an external file because the CSP admits no inline script. `?app=1` forces it for the tab (a device toolbar can fake a phone but not an install), `?app=0` clears it. Back behaves like an app's rather than a browser's (`useAppHistory`): history is kept as `[Home, tab, pages...]`, so switching tabs replaces the tab slot instead of stacking, back from any tab is Home, opening the app deep in puts Home and the page's tab beneath it, and an open dialog gets its own entry so back closes it - generically, by Escape or the dialog's close button, so a new `.modal.show` dialog needs nothing extra. The admin panel follows the same shape inside itself (`useSectionHistory`, used by `SubNav`): the panel holds one history slot that switching section replaces, detail pages (a server, a user) stack on it, so back goes detail -> list -> out of the panel, not through every section visited.
- `src/context/` - `AuthContext`, `SiteContext` (branding and legal pages from `/api/site`), `ToastContext`, `PlayerContext`.
- **File extensions**: React files are `.jsx` - components, contexts and hooks, whether or not they contain JSX. Plain modules stay `.js`: `src/services/api.js`, and `src/services/push.js` (browser push outside React, shared by `usePush` and `AuthContext`).
- `src/services/api.js` - the API client. `VITE_API_URL` is a **build-time** variable and is not set in compose, so production talks same-origin and Nginx proxies to the backend. `npm run dev` proxies `/api` and `/health` through `server.proxy` in `vite.config.js`.
- **Pages load on demand** - every page in `App.jsx` is `page(() => import(...))` (React `lazy`), so the first load carries the frame and one page, and players never download the admin panel. Each renders inside `PageBoundary` (`App.jsx` around the routes, `AdminLayout` around its `Outlet`, so the admin navigation stays put): a loading state that appears after 200 ms, and an error state with a Reload button if a page's chunk cannot be fetched. A failed chunk load reloads the app once on its own first, since after a deploy an app left open asks for chunks the new image no longer has. A new page needs adding as `page(...)`, not a static import.
- **Build** - Vite. `index.html` sits at the root of `frontend/`, not in `public/`; hashed bundles land in `build/static/` (`assetsDir`), which nginx caches for a year while everything else is revalidated. `package-lock.json` is committed and the image runs `npm ci`. Nothing lints during the build any more (CRA used to), so a broken hook rule shows up at runtime rather than failing the image.

## Conventions

- **Game-server modules use flat imports** (`import config`, `import database`) because `src/` is copied to the working directory `/app`. Keep it flat.
- **Backend uses the `src/` package**: new endpoints are blueprints registered in `app.py`, and new tables need an Alembic migration.
- **Console commands go through `commands.py` / `actions.py`.** Nothing else builds a command string.
- **Audit sensitive actions** via `src/utils/audit.py` (`GET /api/admin/audit`).
- **Two independent requirements files** - `backend/` and `game-server/` pin different versions on purpose.
- **Secrets**: `docker-compose.yml` ships dev defaults (`SECRET_KEY`, DB passwords, `API_TOKEN` - compose feeds the manager's `MANAGER_API_TOKEN` from the same value, so the two cannot drift). Override them via `.env` in production and never commit real ones.
- **Tests** are stdlib `unittest`, no extra dependencies, covering the pure security-sensitive logic (command building, action catalog, roster parsing, crash-loop and ack handling, mod-library path containment, the uninstall's path containment and what it promises to keep, the sleeping server's wake filter and the game version it advertises, loot draws, which events grant a box and the period key that makes a grant idempotent, the daily boundary, the Discord relay's URL allowlist, the mail relay's address checks, stack deliveries - one task per stack, whole bundles packed under the per-line cap, only one stack at a time, and a delivery that stops part-way handing back only what did not land - the push relay's endpoint allowlist and VAPID signature, when the crate reminder fires and who it reaches, maintenance - cron reading, the policy's validation, which updates are due, when a planned run may go, the countdown, the hold and the update's refusal to run under a live server - alert routing - who hears an event and which parts of a message stay internal - and the staff feed's one-row-per-alert split from player notifications, and a character's game data - found by owner never by name, the infection kept from its owner, the cache and who may read it, and coins - the earning rule with its link-time baseline, new lives, restored backups and old saves, a bundle selling once, the shop's price floor and daily limit, the gain log and the daily report, and the one-snapshot-per-server sweep with its save-and-wait). Route and authorization tests do not exist yet; nothing in them needs a running stack any more, since the models and blueprints import cleanly against SQLite.

cd game-server && python -m unittest discover -s tests
